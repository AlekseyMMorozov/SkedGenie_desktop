📜 Принятые правила в ходе работы:
Поэтапная работа: один файл за итерацию, с подтверждением перед правкой.
Ничего не придумывать. Источники истины: файл 'files/structure.md' и ответы пользователя.
Из всех вариантов всегда выбирать самый надежный, всегда использовать обработку исключений с логированием.
Архитектура: Domain не зависит от ORM/UI. Infrastructure зависит от Application. Контракты через ABC.
Стек: Асинхронное ядро (asyncio), готовое к миграции на PostgreSQL/веб. Никаких прямых обращений к БД — только через репозитории.
Pydantic v2: используется для валидации и DTO в Domain/Application. ORM-модели изолированы в Infrastructure. Маппинг выполняется в репозитории.
Имена файлов: всегда точно отражают содержимое (без аббревиатур и косвенных названий).
Кодстайл: PEP 8, type hints, f-строки, логирование (DEBUG/INFO/WARNING/ERROR).
Документация: докстринги модулей/классов, краткие комментарии по бизнес-логике, путь в заголовке файла.
Обратная совместимость: Не менять публичные интерфейсы без согласования. Сохранять сигнатуры DTO. Валидация на границах слоёв.
При отправке кода: Полный изменённый блок + справка 1-2 строки. Не генерировать без команды. Проверять на дубли через структуру проекта.
Логирование: Не удалять существующее. Добавлять на границах сервисов и репозиториев. Использовать уровни осмысленно.
Тестирование: На текущем этапе функциональная проверка через UI вместо unit-тестов. Автоматические тесты будут добавлены при стабилизации критических модулей ядра.
Генерация: Ничего не придумывать. Сверять имена/сигнатуры с архитектурным контрактом. Максимально переиспользовать.

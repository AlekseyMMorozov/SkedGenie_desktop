Снимок состояния проекта: Десктопный планировщик смен, нарядов, дежурств (SkedGenie_desktop)
Дата обновления: 2026-05-23
Приоритет: Высокий
Язык: Python
Архитектура: Onion/Clean (Domain → Application → Infrastructure → Presentation)
UI: CustomTkinter

✅ Основная цель:
Реализовать инкапсулированное асинхронное ядро автоматического планирования с проверкой жёстких правил, гибридной оптимизацией, сессионным режимом (undo/redo) и GUI на PySide6. Ядро готово к последующей миграции на PostgreSQL/веб-сервис.
🎯 Текущая задача:
реализация GUI с использованием customTKinter для тестирования функционала crud операций над задачами планирования.
На главном окне: 
Вкладки: Задачи, Графики, Сотрудники, Настройки, 
верхнее меню: Файл/Правка/Вид/Сервис/Справка, 
статус-бар, сворачиваемая панель логов. Без бизнес-логики.

Во вкладке Задачи: Кнопки для КРУД операций и кнопка Обновить, таблица для просмотра задач, уже существующих в БД. Отображается номер записи, название и тип периода.
В диалоговом окне создания новой задачи запрашивает ввод названия и выбор типа периода планирования из списка. есть кнопки Добавить сотрудников, Добавить задействования - пока заглушки. Кнопки Отмена и Сохранить. при сохранении задача сразу же отображается в таблице, а окно создания закрывается. 

В панели логов отображаюся все действия пользователя - что нажал, что ввел, какой получен результат. В файле логов - то же самое. БД в интерфейс не логируется.


🔹 функционала и рабочих потоков
📅 1. Подготовка и настройка
Пользователь создаёт/редактирует справочники: Сотрудники, Виды задействований (смены, наряды, дежурства).
Настраивает матрицу допусков (кто может работать в каком виде).
Задаёт веса неудобств (базовые в weights.json, индивидуальные переопределяются в UI).
Создаёт Задачу планирования: выбирает тип периода (неделя/месяц/год/кастом), опорную дату в календаре → система автоматически рассчитывает границы периода. Выбирает сотрудников и виды задействований (возможно импортировать из другой задачи).
✍️ 2. Ручное предзаполнение
В сетке календаря/расписания пользователь вручную расставляет известные события: отпуска, фиксированные дежурства по приказу, выходные по запросу.
При каждом ручном изменении система мгновенно проверяет жёсткие правила (допуски, макс. часы, мин. отдых, блокировка дня после суточных). Нарушения подсвечиваются.
⚙️ 3. Автоматическое планирование
Нажатие ▶ Запланировать создаёт in-memory сессию.
Ядро запускает оптимизатор: заполняет свободные слоты, соблюдая жёсткие правила, минимизируя целевую функцию:
TotalWeight + α × (Max(IndividualWeight) - Min(IndividualWeight))
В UI отображается прогресс. По завершению сетка обновляется. Генерируется отчёт: какие правила соблюдены, у кого повышенный суммарный вес, какие смены попали в неудобные дни.
🔄 4. Редактирование, откаты, финализация
Все правки после автопланирования пишутся в ActionStack (командный паттерн). Доступны ↩ Откат и ↪ Повтор.
Кнопка ✓ Проверить запускает полную валидацию и выводит детальный отчёт.
💾 Завершить планирование → сессия фиксируется, итоговый график сохраняется в SQLite, промежуточные версии удаляются.
❌ Отменить → сессия очищается, график возвращается к состоянию до запуска планирования.

📜 Принятые правила в ходе работы:
Поэтапная работа: один файл за итерацию, с подтверждением перед правкой.
Ничего не придумывать. Источники истины: файл 'structure.md' и ответы пользователя.
Из всех вариантов всегда выбирать самый надёжный.
Всегда использовать обработку исключений с логированием.
Логически разделять код на отдельные файлы.
Архитектура: Domain не зависит от ORM/UI. Infrastructure зависит от Application.
Стек: Асинхронное ядро (asyncio), готовое к миграции на PostgreSQL/веб. Никаких прямых обращений к БД — только через репозитории.
Pydantic v2: используется для валидации и DTO в Domain/Application. ORM-модели изолированы в Infrastructure. Маппинг выполняется в репозитории.
Имена файлов: всегда точно отражают содержимое (без аббревиатур и косвенных названий).
Кодстайл: PEP 8, type hints, f-строки, логирование (DEBUG/INFO/WARNING/ERROR).
Документация: докстринги модулей/классов, краткие комментарии по бизнес-логике, путь в заголовке файла.
Обратная совместимость: Не менять публичные интерфейсы без согласования. Сохранять сигнатуры DTO. Валидация на границах слоёв.
При отправке кода: Полный изменённый блок + справка 1-2 строки. Не генерировать без команды. Проверять на дубли через структуру проекта.
Логирование: Не удалять существующее. Добавлять на границах сервисов и репозиториев. Использовать уровни осмысленно.
Тестирование: На текущем этапе функциональная проверка через UI.
Генерация: Сверять имена/сигнатуры с контрактом. Максимально переиспользовать код.
